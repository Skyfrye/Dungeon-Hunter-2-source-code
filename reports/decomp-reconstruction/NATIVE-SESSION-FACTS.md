# Facts mined from the Track A "native reconstruction" session (read-only research)

Paths: A = DH_sc/port/android-native/app/src/main/cpp/model_renderer.cpp (35k+ line single TU). T = DH_sc/port/engine-textures/textures.cpp.
Transcripts: S3a = .claude/projects/C--...-DH-sc/3a86b667...jsonl (Track A gameplay), S15 = 15ff0c7e...jsonl (current orchestrator session). "line" = JSONL line index.
Caveat: the Track A session never saw the green bug (it used its own renderer); it only gives the reference pipeline and the original's data-driven behaviour.

## 1. Rendering (BUG A: green characters)

1. Original cache "*.tga" are NOT TGAs for env/character art: they are PVR containers (header 52 bytes, "type 69"). Both `env_x.tga` (4bpp, 524348 B) and `pvr2_env_x.tga` (2bpp, 262204 B) exist for the same texture. [S3a line 8138/8143]
2. Track A decodes these by header, never by name: PVR pixel type 24 = PVRTC 2bpp, 25 = 4bpp, alpha flag = word(h+16)&0x8000, payload at header+52, expected size = max(w,16|8)*max(h,8)*bpp/8, non-mip, power-of-two only, top-origin; output RGBA8 with alpha forced 255 when the alpha flag is clear. [T:60-72, 98-103]
3. TGA path (real TGAs): types 2 only, 24/32 bpp, BGR(A)->RGBA swap (d[0]=s[2],d[1]=s[1],d[2]=s[0]), origin flags honoured. [T:75-87, 104-112]
4. Track A uploads with plain `glTexImage2D(GL_RGBA, GL_RGBA, GL_UNSIGNED_BYTE)`, LINEAR, REPEAT, no mips: the decoder already outputs RGBA, no BGRA upload. A missing texture becomes a 1x1 WHITE texel (never coloured). [A:19805-19840]
5. `pvr2_` name rule: SWAMP terrain asks `pvr2_env_swamp_alpha.tga` directly while the door model asks `env_swamp_alpha.tga`; Track A just stages both names; texture lookup lowercases the name and falls back to `original-cache/data/3d/textures/<lowercased>`. [S3a 1005-1053; A:19525-19535, 19805-19820]
6. Track A material shader is minimal: `gl_FragColor = texture(diffuse, uv) * vertexColour * material_color`; alpha: `original_alpha_blue` -> alpha = AlphaMap.BLUE, else *= AlphaMap.r; discard if a<=alpha_ref. Original GL_Diffuse_L1 shader takes mask from BLUE of AlphaSampler (decoded RGBA, not alpha). Diffuse and AlphaMap share texcoord0. [A:19490-19497; port/irrlicht-android/reference/swamp-render-material-audit/NOTES.md]
7. Mesh attributes: UV = vertex attribute slot 4 (2 floats), colour = slot 2; vertex colour DEFAULT = WHITE (1,1,1,1), overwritten only if the mesh has a colour stream (byte colours /255). Track B's "black moths" fix (colour started black) is the same fact. [A:22912-22918; S15 line 889]
8. Orchestrator note: V1 (S15 970) declared the green look "what the data specifies": swamp creatures use their own character texture sheet and a moss-green patch; mesh/UV/skin weights "check out". RT was told to treat that as unproven (S15 1242). Nobody has compared against the original/Track A pixel-for-pixel: Track A screenshots of Rene/zombie/Bogwomp are the missing reference (Track A mobs are not green: it was never reported there).
9. Earlier S15 line 14619/14838 describe the bug as "streaked" green texture on zombies + companion (not uniform tint), with the jade statue being a genuinely green model. "Streaked" is the signature of a PVRTC decode/stride error, not a channel swap (a swap gives clean wrong hues).
10. Track B has a BGRA hook: `port/decomp-reconstruction/glitch-video/src/gl_function_table.cpp:112-116` rewrites internalFormat to GL_BGRA_EXT when the original passes (GL_RGBA internal, GL_BGRA_EXT data). Any path that does this on RGBA-ordered decoded data swaps R/B (reddish -> bluish, never streaks).

Likely root cause (A): not a lighting/material error. Most probable: the PVR/TGA container decode in Track B's glitch texture path mis-handles the character sheets (2bpp vs 4bpp pick, `pvr2_` variant, header 52-byte offset / stride / alpha-flag, or non-power-of-two) giving green-dominant streaks (PVRTC colour A/B endpoints misread). Secondary: wrong R/B order via item 10. Verify by decoding the character texture (`data/3d/textures/<character>.tga`) with Track A's `dh2_texture_open/decode` (T:60-112) and diffing against Track B's uploaded bytes for the same file; also check that the character mesh binds UV slot 4 and white default vertex colour.

## 2. Factions / aggro (BUG B: monsters attack Rene)

1. Original relation model (reconstructed byte-exact in `port/level-world/character_ai_relations.{hpp,cpp}`): `Relation {enemy, friend_, neutral}`; enemy/friend/neutral come from a per-faction row of `AiFactionEntry` lists in the global AITable factions; enemy sign lookup = `dh2_ai_enemy`. Players/followers are NOT specially excluded: it is purely faction-row data. [character_ai_relations.hpp:7-80]
2. faction id source: Character word +ffc (faction) and +ff8 (AI id): `State{identity, ai_id=resolved[1], faction_id=resolved[0], name, dead}`. GetCharAIFactionId: if cached id < 0 OR >= factions.size() => FALLBACK 10 (AI id fallback 8). [port/level-world/character_ai_classification.cpp:26-34; A:2142-2160]
3. Therefore a follower/NPC whose faction property is unset or out of range silently becomes faction 10 and can be an enemy of monsters. Rene: SWAMP `_prim_NPC_*`, AITable type 2 (follower) row, script "rene"; faction must come from his property row, not a default. [A:2120-2125; S3a 32942]
4. The Track A aggro scan: `update_enemy_acquisition` walks the CharacterList (all Characters incl. Prince, faery, Rene) and calls `dh2_aggro_target_search_object_list` with `source_relation_for_ooi(owner,candidate,enemy/friend/neutral)`; targeting is gated by `AI_IsEnemy`, so friendly NPCs are never picked. Monster with a target or master returns early (no rescan). [A:30146-30215; A:15079, 15408, 15537, 15622, 19348]
5. Auto-target of the PLAYER also requires `AI_IsEnemy(Player,candidate)`: the emulator test had the player hitting the friendly priest until this was added. [S3a 7473, 8065]
6. Rene is a follower (AITable type 2, not IsMonster): he scans every turn, his AIS `OnEnemySpotted -> GrabTarget` sets target_40 to an ENEMY Character, `update_follower_enemy_target_v1` drives melee/range events. The monster side does NOT treat him specially: monsters pick targets by faction relation, and Rene being nearer than the Prince is fine if enemy. [A:30430-30548; S3a 32942]
7. Monster/Rene mutual targeting list: Rene must appear in the monster's out/in aggro lists; kill credit walks all attackers (CharAI::OnDeAggro for follower peers is accepted). A previous Track A crash came from the aggro list only accepting monsters. [A:28286-28292; S3a 33113, 33361]
8. Earlier Track A bug "mobs don't aggro": "a wrong argument check in the target-search code failed every monster's search" [S3a 3028, fixed ~2989].
9. Companion Faery same mechanism: a native Faery/Rene is an ordinary Character with faction from property; `Query::player`/`follower`/`faerie` are classification flags (A:3966-3990, 12446-12461).

Likely root cause (B): in Track B the faction ids for the NPC/follower (and probably the Player) are either not loaded or fall to the fallback (id 10 when property < 0 or >= count), or the faction-row friend/neutral entries are never consulted (code treats every non-self Character as an enemy / doesn't call AI_IsEnemy in the candidate filter). Check (a) the faction property read for Rene's Character row, (b) that `factions.size()` is the loaded global count, (c) that the aggro target filter applies enemy-relation (character_ai_relations `query(Relation::enemy)`) per candidate and uses `Query::faction_id`, not AI id.

## Port fact: targetSdk 35 (SDK1)

The source-built and bundled APKs target SDK 35 (minSdk 26, compileSdk 37). The data root is still /sdcard/Android/data/com.gameloft.android.GAND.GloftD2SS/files/ (app-specific external dir: no permission needed under scoped storage; native fopen, DataSetup unpack, saves, dh2_session.txt and the dh2_report.zip share through SessionProvider verified on an API 37 emulator). Port-only Java changes for the 28 -> 35 behaviour differences are marked "Port (SDK1)": PortCompat.java (registerReceiver flag, Bluetooth runtime permissions, PhoneStateListener), GLBluetooth.init/create (no adapter / no permission = Bluetooth unsupported), Musicplayer playlist query (MediaStore rejects the "*" projection at target 30+: empty playlist list), GameInstaller PendingIntent.FLAG_IMMUTABLE, DataSetup (the Download folder is invisible to apps on Android 11+; use the obb dir or the app files dir for an unbundled archive), manifest (maxSdkVersion on legacy storage/Bluetooth permissions, enableOnBackInvokedCallback=false so Back stays KEYCODE_BACK). The origdex variant (original unpatched dex) stays at targetSdk 28 (build_release.py --orig-target-sdk).
